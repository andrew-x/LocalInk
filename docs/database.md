# Database

Localink uses Drizzle ORM with a locally stored SQLite database. Database code lives under `src/lib/drizzle`, with schema in `schema.ts` and generated SQL migrations in `src/lib/drizzle/migrations`.

## Data Mode

Set `LOCALINK_DATA_MODE` in `.env`:

```env
LOCALINK_DATA_MODE=dev
```

Valid values are `dev` and `prod`. If the variable is omitted, Localink defaults to `dev`.

Database files are stored under the mode-specific app data folder:

- `data/dev/localink.sqlite`
- `data/prod/localink.sqlite`

The app creates the mode folder when it opens the database. `data/` contents are ignored by git because they contain local user data.

## Schema

The writing model has five content tables and one app metadata table:

- `stories`: `id`, `name`, `description`, `characters`, `style`, `created_at`, `updated_at`
- `chapters`: `id`, `story_id`, `name`, `position`, `content`, `indexed_hash`, `indexed_at`, `summary`, `updated_at`
- `chunks`: `id`, `story_id`, `chapter_id`, `text`, `start_position`, `end_position`, `embedding`
- `story_chats`: `id`, `story_id`, `title`, `created_at`, `updated_at`
- `story_chat_messages`: `id`, `story_id`, `chat_id`, `role`, `is_visible`, `position`, `content`, `generation_id`, `created_at`, `updated_at`
- `metadata`: `key`, `value`, `updated_at`

`chapters.story_id` references `stories.id` with cascading delete behavior. `chapters.position` stores the chapter order within a story, and `chapters_story_position_idx` supports loading chapters by story in order.

`chapters.indexed_hash` stores the SHA-256 hash of the chapter `content` string that was last successfully indexed. Content save actions do not update it. The indexing columns and helpers are retained, but editor autosave currently does not trigger indexing; prose generation uses full chapter manuscript content instead of indexed summaries or chunks. When indexing is enabled again, it should compute the current content hash on demand and advance `indexed_hash` only after summary, chunk, and embedding data has been refreshed. `chapters.indexed_at` stores the timestamp for that successful indexing pass and is nullable for chapters that have not been indexed by the background job.

`chunks` stores paragraph-bounded chapter text slices, original-content offsets as `[start_position, end_position)`, and nullable serialized embedding vectors. Embeddings are stored as sqlite-vec-compatible float32 vector BLOBs; the `chunks_embedding_float32_vec_check` constraint rejects non-BLOB or non-float32 vector values while still allowing `NULL` when a chunk has not been embedded yet. `chunks.story_id` and `chunks.chapter_id` both cascade on delete. `chunks_chapter_position_idx` supports loading chunks by chapter in text order, and `chunks_story_idx` supports story-scoped retrieval.

`story_chats` stores story-scoped planning chats. Chat rows belong to a story and cascade on story delete. The `story_chats_story_updated_idx` index supports loading recent chats for a story history picker.

`story_chat_messages` stores ordered chat messages. Visible messages use `role` values of `user` or `assistant`; hidden style-and-character context snapshots use `role = 'system'` with `is_visible = 0` and intentionally exclude story description, chapter summaries, manuscript text, retrieved excerpts, and outline content. Each prepared generation stores a hidden context snapshot row with a `generation_id`, and the saved assistant reply stores the same `generation_id` for traceability. `story_id` and `chat_id` both cascade on delete. `story_chat_messages_chat_position_idx` supports loading visible chat history in order, and `story_chat_messages_generation_idx` supports validating prepared generations before streaming or saving output.

`stories.characters` stores a JSON array of `{ id, name, description }` objects for story-level character context. Character IDs are hidden from users and generated by the server when missing. `stories.style` stores story-level prose/style guidance as text.

`metadata` stores global app settings and small local bookkeeping values. The `ai.systemInstructions` key stores the user-configured global AI system instructions. Missing or blank values mean LocalInk uses only its built-in system prompts. The setting is global to the local app, not scoped to a story.

`stories.created_at`, `stories.updated_at`, `chapters.updated_at`, `story_chats.created_at`, `story_chats.updated_at`, `story_chat_messages.created_at`, and `story_chat_messages.updated_at` default to the current UTC timestamp on insert. SQLite triggers refresh the story and chapter `updated_at` fields automatically on row updates when the write does not explicitly change `updated_at`; chat actions write chat and message timestamps explicitly.

## Migrations

Migrations are generated from the TypeScript schema:

```bash
bun run db:generate -- --name=<migration-name>
```

Migrations can be applied manually:

```bash
bun run db:migrate
```

They also run automatically when the Next server starts. `src/instrumentation.ts` calls the migration runner only in the Node.js runtime, before the server starts handling requests. The shared better-sqlite3 connection loads sqlite-vec before migrations run so migrations and constraints can call sqlite-vec functions such as `vec_type`. Drizzle tracks applied migrations in SQLite with its `__drizzle_migrations` table, so repeated starts are no-ops unless new migration files exist.

Migration `0007_chapter-indexing` renames existing `chapters.hash` values to `chapters.indexed_hash`, treating those local values as already indexed. It does not run a one-time reindex or backfill.

Migration `0009_rename-metadata-table` renames the original `localink_metadata` table to `metadata` with `ALTER TABLE`, preserving existing local key/value rows.
