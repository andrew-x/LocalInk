# AI Image Generation

Generated assets are stored locally, but generation sends prompts to the selected provider. Privacy depends on verified routing and sanitized logs, not on local storage alone.

## Provider Flow

All currently offered models route through OpenRouter; a dormant WaveSpeed adapter remains for historical compatibility. Chat-style image models use chat completions, while native image models reject that endpoint and require `/api/v1/images`. Native responses can contain bare base64 plus a media type without a response ID.

Endpoint choice cannot be inferred from model names or modalities. Compare the chat and image catalogs: an image-catalog entry absent from the chat catalog needs the native endpoint. Presence in the image catalog alone proves nothing because chat-style models may appear in both.

Native endpoints validate per-model parameter enums. Capability maps in code are the source of truth for clamping sizes, selecting the nearest supported aspect ratio, or omitting unsupported fields. Do not assume the app's size choice affects a model that declares no resolution parameter.

### Zero Data Retention Routing

New image models require ZDR by default. Models without eligible endpoints need a deliberate image-only exemption; such exemptions never apply to text calls. Endpoint behavior determines how this promise is enforced.

The [ZDR catalog](https://openrouter.ai/api/v1/endpoints/zdr) check on 2026-10-06 found no eligible endpoints for `openai/gpt-image-2.5-sunburst`, `openai/gpt-image-2.5-flare`, `qwen/qwen-image-3-pro`, `x-ai/grok-imagine-image-2.0`, `sourceful/riverflow-v2.5-pro`, `black-forest-labs/flux-3-image`, or `google/gemini-nano-banana-2.1`. These exact IDs were deliberately exempted for image calls. This is historical evidence for those privacy decisions, not a live availability guarantee; the current exemption set lives in `src/lib/generated-images.ts`.

**`/api/v1/images` ignores `provider.zdr`.** Verified 2026-08-16 against the live API: a request for `qwen/qwen-image-3-pro` (which has no ZDR-listed endpoint) with `provider: { zdr: true }` returned an image instead of refusing, where the same constraint on `/api/v1/chat/completions` correctly refuses with "No endpoints found matching your data policy (Zero data retention)". The flag alone is therefore decorative on the images endpoint.

The native endpoint does honor `provider.only`. Require eligible provider slugs with `allow_fallbacks: false` alongside the ZDR flag. Slugs come from the ZDR catalog's `tag` field and must match `available_providers` in an invalid-provider response; the current mapping lives in code. The recorded eligible slugs were `seed` for Seedream, `krea` for Krea, and `tencent` for HY.

Rechecked 2026-10-06: synthetic requests for Flash and HY with a deliberately invalid `provider.only` returned 404, with `available_providers` listing `seed` and `tencent`, respectively. No images were generated by these probes. The [image generation guide](https://openrouter.ai/docs/guides/overview/multimodal/image-generation) still lists native-image routing fields `only`, `order`, `ignore`, `sort`, and `allow_fallbacks`, without `zdr`; this refresh preserves the pinned-provider safeguard rather than treating the flag as enforcement.

Chat completions enforces `zdr` without native-endpoint slug pinning. An explicitly exempt image model omits that routing even when it uses chat completions.

Privacy-routing refusals become `AI_ZDR_UNAVAILABLE`, without fallback to a retaining provider. Both ZDR refusal wording and pinned-provider refusal wording matter because provider pinning enforces the native endpoint's privacy boundary.

### Adding Or Updating A Model

For every exact model ID, including version upgrades:

1. Compare the [chat catalog](https://openrouter.ai/api/v1/models) and [image catalog](https://openrouter.ai/api/v1/images/models) to select the endpoint.
2. Check the [ZDR endpoint catalog](https://openrouter.ai/api/v1/endpoints/zdr). Record the result and date; text without ZDR must be rejected, while an image-only exemption must be deliberate.
3. For native images requiring ZDR, obtain eligible provider slugs and verify `provider.only` enforcement with an invalid-provider request. Check returned `available_providers`; keep fallbacks disabled. Do not trust `provider.zdr` alone.
4. Check per-model image endpoint parameter enums and upstream prompt caps before updating capability and prompt-shape maps. Catalog availability alone does not demonstrate successful generation or output quality.

### Prompt Decisions

Affirmation-only prompts are conservative choices for some models, not proof of their architecture or negation handling. Prompt-capped models prioritize the subject over style expansion, preserving user intent within the upstream limit.

Skin realism is described through texture and tone rather than repeated lesion words. Repetition across style, system guidance, and prompt layers amplified acne/redness; condition nouns belong only in negative prompts for models that can use them. Similarly, words such as “unretouched” and “documentary” were generalized to dirty settings. Prompts distinguish an unstyled photograph from an unclean place, and enhancement must not invent decay.

### WaveSpeed (Dormant)

Historical rows retain their WaveSpeed provider/model IDs even though no current model uses that adapter. Its provider type remains valid rather than being inferred solely from today's model list.

The adapter gates fields by provider schema because undeclared parameters are rejected. It disables provider prompt expansion where supported so that a second rewriter does not fight LocalInk's composed prompt. Output can be base64 or a CDN download; inspect actual image bytes rather than assuming PNG or trusting response headers.

Prediction deletion is best-effort privacy cleanup. On success it follows durable local file and database persistence; failed generations also attempt deletion because their prompts may remain remotely. Cleanup failure must not turn a successful local generation into an error. There is no historical backfill, and deleting a local image does not contact the provider. Stored prediction IDs may therefore refer to already-deleted remote records. OpenRouter has no equivalent cleanup endpoint in this integration.

## Local Storage

Image files and SQLite metadata share the selected `data/<mode>/` isolation boundary. Paths are stored relatively; server resolution rejects absolute paths, traversal, and escapes from the generated-images directory.

`prompt` means the description actually sent. `original_prompt` is present only when enhancement replaced the writer's wording; null means `prompt` is the original wording. Older rows cannot recover originals that were never saved. User-facing descriptions prefer the original, and prefilling restores the enhancement separately rather than silently replacing editable user text.

Retired or unknown model IDs normalize to the current default only when prefilling a generation form. Stored rows retain the actual generating model; compatibility normalization must not rewrite history.

## Concurrent Generation

Generation uses a mutation Route Handler because client Server Actions serialize calls. Preserve the [action-boundary safeguards](backend-actions.md#route-handler-carve-out). The gallery is already dynamic, so this route does not need the former action's path revalidation.

The concurrency cap leaves browser connection headroom for navigation, thumbnails, and prompt enhancement; it is not a provider rate limit. Jobs are session-local rather than durable queue records. A completion does not take the stage from an explicitly selected image; per-job failures stay associated with that job rather than becoming form-global failures.

Navigating away abandons the browser request but does not cancel server generation: completed images still reach local storage and the gallery. This is a deliberate scope decision, not an implied cancellation guarantee.

## Logging And Privacy

Prompts, output text, images, provider bodies, and local paths are private. Log sanitized operational metadata only. Provider moderation errors can quote the submitted prompt, so replace them with coarse rejection codes rather than logging the message.

### Failure Logging

Generation failures have one structured `image-generation-failed` record. Provider errors are reduced to bounded scalar metadata and short sanitized messages; raw objects must not pass through those fields. Refusal output is never logged because it can restate the prompt. Non-JSON gateway errors still need sanitization before useful infrastructure details are retained.
